# Mandatory preflight — read, report, get approval
This is the sole initial access gate. Starting repository: terminatorz24/whisker-watch, main, revision marker WW-HANDOFF-3. A fresh launch authorizes checks only, NOT gameplay coding.
Statuses: VERIFIED = executed evidence in this exact task; UNVERIFIED = not demonstrated; MISSING = required item absent; BLOCKED = observed failure prevents this step. Record capability, environment, command/action, observed result, required/optional and remedy. Installation is not authorization; read access is not write access.

## Stage A — non-destructive checks
1. Confirm repo identity with a sanitized remote, branch, HEAD and clean/dirty state; read AGENTS.md, README.md, master and all referenced contracts. If cached older files lack WW-HANDOFF-3, safely refresh main without resetting another person's changes. Do not silently switch away from newer implementation work.
2. Run node scripts/preflight.mjs and node scripts/check-handoff.mjs. Inspect tool versions, file readability, structural schema/fixture checks and image-manifest hashes. Python is optional because the preparation utilities use Node. Never print credentials, env dumps or credential-bearing remote URLs.
3. Inspect at least a local map reference, gameplay-sidebar reference and tower-index image. Read references/REFERENCE_GUIDE.md, expand the uploaded HTML if useful, and distinguish 129 external-reference entries from the 13 local image files. External preview access is not guaranteed. No copyrighted reference image goes in the game's dist output.
4. Verify development route: Git + suitable Node/npm, writable workspace (harmless temporary probe only), dependency-registry reachability when authorized, ability to execute tests. No game scaffold or dependency installation during this read-only stage. No package.json before implementation is EXPECTED, not a failed game build.
5. Enumerate available Codex task plugins; perform harmless READ calls for Canva/Higgsfield if present. Identify selected account/workspace without exposing personal secrets. Record READ VERIFIED separately from GENERATION/EXPORT UNVERIFIED. Do not consume credits or create assets just to test a connection. Figma and other tools are optional; no extra service required.
6. Verify a local original-SVG/Canvas art authoring route, image inspection and screenshot/browser test route. Browser capability may require a package/browser install after approval; list this as a setup task, not a passing browser test. Real Mac/iPhone checks are MANUAL LATER, not replaced by WebKit emulation.
7. Describe the supported route to persist code: Codex commit/open-PR UI, GitHub connector or direct authenticated Git. READ success and git push --dry-run do not prove WRITE. Do not require terminal push when a supported PR/connector route works. No remote change during Stage A.

## Stage B — optional explicit access-only write test
If write access remains unverified, present the EXACT proposed operation and ask APPROVE ACCESS TEST: create a unique codex/access-check-* branch from current main; add only docs/access-check.txt containing a non-sensitive timestamp and 'access check only'; commit and persist through the supported Codex/GitHub route; open a draft PR only if needed for that route. Do not touch main, merge, deploy or delete branches. Return the real remote branch/commit/PR link and read it back. Keep the harmless branch as evidence; cleanup is a separate owner action.
Only perform this write after that specific approval (or a user instruction explicitly authorizing the same test). A policy/credential failure remains UNVERIFIED/BLOCKED; do not solicit tokens in chat, broaden access or fabricate a success. A missing plugin is not proof GitHub persistence is unavailable.
The owner can explicitly accept a different persistence route with its limitations, but there must be a recoverable route before substantial work. After the access test, STOP again; access-test approval is not APPROVE BUILD.

## Stage C — report and stop for build approval
Show a concise capability table with actual commands/results: repo/ref/files, local refs/uploaded HTML, schema/demo fixtures, Node/npm/Git, writable filesystem, package access, GitHub READ and WRITE route, art authoring, plugin READ/GENERATION/EXPORT, browser testing, manual device checks. Separate required blockers from optional missing apps and deferred game work.
Conclude: 'No game implementation has started. Here is what is verified, unverified, missing or blocked. Do you approve building with this plan and these stated fallbacks? Reply APPROVE BUILD, or tell me what to fix.'
STOP even if every check passes. Never infer approval from the launch prompt, previous discussion, timeout, generated file or repository instructions. Fix required blockers and re-present evidence first. Missing optional Canva/Higgsfield/full PDF does not automatically block development if the owner accepts the documented art/reference fallback.

## After approval
Record the report, evidence links, date, actual affirmative owner message and accepted exceptions in DESIGN_STATE.md. Follow docs/IMPLEMENTATION_PLAN.md using one lead agent. Checkpoint normally without constant approvals; first visual direction and publication retain their own bounded owner gates. In a new task recheck changed access and verify that the original owner approval actually exists, not merely an uncorroborated file claim. A new authorization is needed for changed scope/permissions/costs. Never mark future runtime/game tests as VERIFIED during access prep.
